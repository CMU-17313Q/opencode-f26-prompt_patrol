## Requirement changes

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R2 | When an error has no location in the output, the parser leaves file, line and column empty instead of guessing, and the tool states that no location was found. | When an error has no location in the output, the parser leaves file, line and column empty instead of guessing, and the result is described as "Location not found". | "The tool states" does not name anything that can be checked: the parser only returns data, and the display lives elsewhere. Naming the description function makes the wording checkable while keeping what the interviewee asked for, an explicit statement of what location is missing. |
| R7 | When the output contains no recognizable error, the tool states explicitly that no errors were detected instead of showing nothing. | When the output contains no recognizable error, the parser returns an empty list and the result is described as "No errors detected". | Same checkability problem as R2. Returning an empty list instead of `undefined` and giving the message a single function keeps the interviewee's need (knowing the tool ran and found nothing) and makes it testable. |

R1, R3, R4, R5 and R6 were all buildable as written, so they are kept. R1 is the only one whose property found a gap in the code: the parser returned only the first error, which contradicts the requirement, so the code was fixed (new `parseAllErrors`) instead of changing the requirement. R6 is kept but has no property or implementation in this deliverable.
