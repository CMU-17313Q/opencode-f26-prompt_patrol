### R5: supported patterns and outgoing boundary

This is a proposed protection contract; it is not an existing redaction feature.

- **Named credential fields:** case-insensitive, whole-key matches for `API_KEY`, `PASSWORD`, `PASSWD`, `SECRET`, and `ACCESS_TOKEN`, followed by optional spaces/tabs, `=` or `:`, optional spaces/tabs, and a nonempty value. A key starts at the beginning of a string or after a non-letter/digit/underscore. Values may be single-quoted or double-quoted on one line without escaped quotes, or unquoted. An unquoted value ends at whitespace, a quote, comma, semicolon, or closing bracket/brace/parenthesis. Quoted values end at their matching quote. This includes `API_KEY=TEST_SECRET_123` and `password="example password"`.
- **Bearer credentials:** case-insensitive `Authorization`, optional spaces/tabs, `:`, optional spaces/tabs, `Bearer`, at least one space/tab, and a nonempty token composed of letters, digits, hyphens, periods, underscores, tildes, plus signs, slashes, or equals signs. Apply the same whole-key start boundary as above.
- **Replacement:** replace the identified secret value with `[REDACTED]`; remove repeated copies of that identified value from all model-visible strings in the request. Preserve nonsensitive labels and diagnostic content where this does not retain a detected secret.
- **Boundary:** inspect the final model-visible payload immediately before dispatch to the configured AI provider, after history selection and any message transformations. Include user/system text, assistant history, tool arguments, tool results, and error messages that are actually sent. This scope excludes transport authentication headers required to authenticate to the provider. It does not promise detection of arbitrary unlabeled secrets or secrets embedded in binary attachments.
- **Acceptance check for later work:** use synthetic credentials in each supported format and in repeated command/output/history copies. Capture the outgoing model-visible payload and verify that none of those secret values remain and that replacement markers appear. Include the original P4A `TEST_SECRET_123` example. No such test is implemented in this step.

### P4B review checks and current implementation limits

The main table supplies the P4B acceptance criteria; the Original P4A source record preserves the earlier criteria. The following clarifications describe the scope of later checks, not test results.

- **R1:** check the eligibility and visibility conditions independently. The helper can detect a tool error without metadata.output, but the current UI does not show its button. Hiding tool details also hides completed tool parts, including nonzero exits. A timeout or abort that leaves a completed state with an unknown exit is ineligible. A nonempty command is not necessarily nonblank: the current helper does not trim command text. Numeric exit detection uses `typeof value === "number"`, not a finite/integer check.
- **R3:** check empty output, tool-error fallback, unknown exit, and lengths below, at, and above 4,000. The fallback state.error is not ANSI-stripped or trimmed by the existing helper. Upstream capture can already have shortened metadata.output, and expanding the UI output does not enlarge the generated explanation. No structured file-location field is attached by this helper.
- **R4:** with two different failed executions, selecting either button should populate the new explanation with that execution's data, including when selecting the older one. Historical messages may still contain the other error.
- **R5:** unmet at the inspected commit. The explanation helper copies command/output into the prompt, and session history can separately carry the original tool data. No protection described in the R5 contract has been implemented here.
- **R6:** use two separate failed execution states, not just two strings derived from one request. Their filenames differ while the error type, command, and exit stay fixed. Each state is processed independently, and both requests must retain their own filename and the shared error type. Keep those markers wholly inside the retained output and compare Error output sections; session history may legitimately contain both runs. This checks data isolation in the helpers, not UI selection wiring.
- **R8:** check that a normal follow-up uses the same session ID and includes the context retained by history selection. After compaction, assess the retained history/summary instead of requiring the original explanation verbatim.

The R2 invariant exercises failedCommand, which feeds Shell's failure() memo. The explanation button is nested under Show when={failure()}, so an undefined helper result supplies the false condition needed to hide the button for successful or unfinished executions. This supports the eligibility part of R2 but is not a full UI proof: it cannot catch a removed/bypassed guard, stale reactive state during status transitions, incorrect tool-part wiring, or an accidentally rendered button. It also does not exercise the parent-session restriction, metadata.output block selection, showDetails visibility, or click/submission behavior. Those need separate component or integration checks; no such checks are claimed here. The R3, R6, and R7 properties check generated explanation text; they do not establish R5 protection for the whole outgoing payload or validate AI answer quality. The button uses the ordinary prompt setter and submitter; it currently does not reset shell mode, so an explanation click while the composer is in shell mode is a separate known submission limitation.
